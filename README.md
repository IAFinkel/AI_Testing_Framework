# AI Agent Evaluation Framework

A personal project - testing framework for AI agents,
built by writing a small evaluation harness from scratch and, in parallel, adopting
[DeepEval](https://deepeval.com) — a purpose-built LLM/agent evaluation library —
for the metrics where a mature library outperforms a hand-rolled one.

The project runs entirely locally on a single machine, uses free-tier models on
[OpenRouter](https://openrouter.ai) as the LLM judge, and evaluates a small set of
sample agent conversation traces against hand-written ground truth.

## Why this project exists

The goal is to understand, hands-on,
how agent evaluation actually works: what an LLM-as-judge pattern looks like in
practice, where it's fragile, what a mature library like DeepEval gives you for
free versus what you still have to build yourself, and how much of "the tests
pass" is actually trustworthy versus an artifact of the test data happening to be
simple.

That last point ended up being the real lesson of the project. Almost every
finding below was discovered not by reasoning about the code in the abstract, but
by running it against a new piece of real data and watching it fail in a way
nobody had anticipated — then figuring out why. **Verify empirically, don't trust
documentation or your own first draft** became the project's actual working
principle, more than any specific line of code.

directly.

## Setup

A single shared `.env` file at the project root, read by every script:

```
OPENROUTER_API_KEY=sk-or-...
OPENROUTER_MODEL=nvidia/nemotron-3-ultra-550b-a55b:free   # optional, this is the default

# Only relevant to task_complition_metric_test.py; see "TaskCompletionMetric" below
DEEPEVAL_PER_TASK_TIMEOUT_SECONDS_OVERRIDE=600
DEEPEVAL_RETRY_MAX_ATTEMPTS=2
```

Dependencies:

```bash
python3 -m pip install openai python-dotenv deepeval --break-system-packages
```

Every script locates the shared `.env` with `find_dotenv()`, which walks upward
from the script's own location until it finds one. This matters here
specifically: `eval_tools/custom/` and `eval_tools/deepeval/` sit two levels
below the project root, and `find_dotenv()` handles that correctly without any
script needing to know or hardcode how many levels deep it happens to live.

## The scripts

### `preprocess/data_extract_new.py` — trace normalization

Takes a raw agent execution trace and normalizes it into:

```json
{
  "user_request": "...",
  "planner": [...],
  "router": [...],
  "tools": [...],
  "turns": [
    {"user_request": "...", "planner": [...], "router": [...], "tools": [...]},
    ...
  ]
}
```

The top-level `planner`/`router`/`tools` fields are a flattened view across the
whole trace, kept for backward compatibility with single-turn traces and every
script below (none of which read `turns` yet — see **Known limitations**).
`turns` is always present and always correctly scoped to one turn each, useful
for inspecting a multi-turn conversation without everything blurred together.

Handles three distinct real-world shapes, found by testing against three actual
sample files rather than one:
- **TC1-style**: `{"steps": [...]}`, with `tool_call` events carrying input and
  output together on a single event.
- **TC2-style**: already pre-structured (`{"planner": [...], "router": [...], "tools": [...]}`)
  — passed through, wrapped as a single-element `turns` list for consistency.
- **TC3-style**: a bare list of `human` / `agent_plan` / `agent_action` /
  `tool_output` / `agent_finish` events, potentially spanning several
  conversation turns.

```bash
cd preprocess
python3 data_extract_new.py ../input_data/agent_history_tc_1.json -o extracted_data_tc_1.json
```

### `eval_tools/custom/custom_metric_agent_plan_test.py` — Planner

LLM-as-judge, PASS/FAIL per plan step, comparing an agent's plan against a
ground truth. The judge's own rubric only fails a step if something required is
*missing, incorrect, or out of order* — it does not penalize an extra,
harmless step. That's a deliberate design choice in the prompt, not a bug (see
**Precision vs. Recall vs. Planner**, below).

```bash
cd eval_tools/custom
python3 custom_metric_agent_plan_test.py --predicted ../../preprocess/extracted_data_tc_1.json --ground-truth ../../input_data/ground_truth_tc_1.json
```

### `eval_tools/custom/custom_metric_agent_plan_precision_test.py` — Precision

Scores what fraction of the *actual* plan's steps were correct: `TP / (TP + FP)`.
Penalizes extra or wrong steps that Planner's PASS/FAIL rubric lets slide.

Reports both a **macro-average** (mean of each step's own precision) and a
**micro-average** (pool every step's TP/FP first, then divide once). These are
legitimately different numbers whenever steps carry unequal weight (a step
covering 3 sub-actions counts the same as a 1-sub-action step in the macro
figure, but 3x the weight in the micro figure) — this is expected and
structural, not a bug.

Also validates the judge's own arithmetic: if a step's reported `true_positives`/
`false_positives` don't match its own reported `precision` value beyond a small
tolerance, the score is recomputed from the counts (which are trusted, since
they're just integers) and flagged via a `precision_corrected` field, rather
than silently trusting a judge that may have contradicted itself.

### `eval_tools/custom/custom_metric_agent_plan_recall_test.py` — Recall

Mirrors Precision, scoring what fraction of *expected* steps were actually
accomplished: `TP / (TP + FN)`. Penalizes missing steps. Same macro/micro
averaging and self-consistency correction as Precision.

**Known limitation**: matches steps by list *position*, not by matching their
actual content. A plan that correctly performs every required step but in a
different order would misreport as having missing/extra steps. This was a
deliberate, acknowledged trade-off (true order-independent matching would need
comparing each step against the *entire* other plan, not just the same index) —
not something discovered by accident, but not fixed either.

### `eval_tools/deepeval/tools_call_test.py` — DeepEval `ToolCorrectnessMetric`

Uses DeepEval's built-in metric instead of a hand-rolled judge: did the agent
call the right tools, with the right arguments, producing the right output.
Configured with `evaluation_params=[ToolCallParams.INPUT_PARAMETERS,
ToolCallParams.OUTPUT]` so the score reflects more than just tool *names*.

Includes a supplementary `diff_tool_calls` function that reports a field-level
diff (which specific input parameter or output differed) independent of
whatever DeepEval's own `reason` text says — added because the `reason` text
was found to use the same "missing tools" phrasing for both a total miss and a
partial parameter mismatch, which is easy to misread.

```bash
cd eval_tools/deepeval
python3 tools_call_test.py --predicted ../../preprocess/extracted_data_tc_1.json --ground-truth ../../input_data/ground_truth_tc_1.json
```

### `eval_tools/deepeval/task_complition_metric_test.py` — DeepEval `TaskCompletionMetric`

Referenceless — no ground truth needed. Judges, per conversation turn, whether
the agent's response actually accomplished what the user asked, using an LLM
judge with no fixed reference to compare against. Reads a raw trace directly
(not the `preprocess/`-normalized output the other scripts use).

```bash
cd eval_tools/deepeval
python3 task_complition_metric_test.py --history ../../input_data/agent_history_tc_1.json
```

This is structurally different from the other four scripts (see the comparison
below) and needed the most iteration of anything in this project — see the bug
list for the full account.

## Precision / Recall / Planner vs. Task Completion — when to use which

| | Ground-truth based (Planner/Precision/Recall/Tool Correctness) | Referenceless (Task Completion) |
|---|---|---|
| Needs a hand-written ground truth | Yes | No |
| Needs `data_extract_new.py` normalization | Yes | No — reads the raw trace directly |
| Best suited for | A known-correct procedure that must be followed exactly (compliance steps, required tool sequences) | Open-ended requests where multiple valid paths could satisfy the user |
| Score stability across reruns | Anchored to a fixed reference — a score change reflects a real behavior change | Can drift between runs on *identical* input, since there's nothing to check the judge against (see Bug #21) |
| Practical use | The right choice for a CI gate | Better as a broader monitoring signal, cross-checked before trusting a specific number |

## Bugs found during development

Roughly in the order they were discovered. Nearly every one of these was found
by running real test data through the scripts, not by code review — several
were only caught because a *third* differently-shaped test file was tried after
the first two had already passed.

### `data_extract_new.py`

1. **Router filter silently dropped sub-agent tool calls.** The original filter
   only captured `agent_action` steps where `agent == "RouterAgent"` — a tool
   invoked directly by a sub-agent (e.g. `ConversationalBot` calling
   `RAGRetriever`) matched no branch at all and vanished with no trace or
   warning. Fixed by accepting any `agent_action`, regardless of which agent
   performed it.
2. **`route_to` and `tool` were mutually exclusive** (`if`/`elif`). A step that
   both routed to a sub-agent *and* invoked a tool as part of that decision had
   its `tool`/`tool_input` silently discarded. Fixed to record both,
   independently.
3. **`user_request` was a plain overwrite, not a capture-once.** On a
   multi-turn trace, every human turn overwrote the last, so only the *final*
   user message ever survived into the output.
4. **No concept of conversation turns at all.** A 4-turn trace's `planner`/
   `router`/`tools` were merged into one flat, undifferentiated list — step 1
   from turn 1 and step 8 from turn 4 sat side by side, indistinguishable.
   Fixed by adding a `turns` field that segments output per human turn, while
   keeping the flattened top-level fields for backward compatibility.
5. **TC1-style `tool_call` events lost their input entirely.** These events
   carry both `input` and `output` on a single event (unlike the two-step
   `agent_action` + `tool_output` pattern), but the original script only ever
   filed them into `tools` (output only) — they never populated `router` at
   all, meaning there was never anything to compare tool *arguments* against
   for this trace shape.

### Planner / Precision / Recall (shared logic)

6. **`response.choices[0]` crashed with `TypeError: 'NoneType' object is not
   subscriptable`** whenever OpenRouter returned an error/rate-limit response
   instead of a normal completion — the code never checked whether `choices`
   was actually present before indexing it.
7. **`zip()` truncation.** Comparing actual vs. expected plans with plain
   `zip()` silently drops any steps beyond the length of the shorter list — an
   agent producing 3 steps against a 4-step ground truth (or vice versa) never
   surfaced the missing/extra step anywhere in the report. Fixed with
   `zip_longest` and explicit handling of both "extra" and "missing" cases.
8. **OpenRouter's documented `models` fallback array doesn't reliably trigger
   on transient provider errors**, contrary to what the docs describe — this
   was tested directly (an artificially broken primary model, and a real
   Nvidia 502 overload) and confirmed the fallback array sometimes never
   engages even when it should. Client-side retry-with-backoff is the
   mechanism that actually works.
9. **(Precision/Recall specific) No validation that the judge's own numbers
   were self-consistent.** A judge can return a `precision`/`recall` value
   that mathematically contradicts its own `true_positives`/`false_positives`
   (or `false_negatives`) counts. Added a check: recompute from the counts
   (trusted, since they're plain integers) whenever they disagree with the
   reported ratio beyond a small tolerance, and flag it in the report rather
   than silently trusting either number.

### `tools_call_test.py`

10. **`ToolCorrectnessMetric` requires a configured judge model, despite
    DeepEval's own FAQ claiming the score is "mostly deterministic" and
    doesn't need one.** Confirmed empirically — it raised
    `OpenAI API key is not configured` even in a configuration with no
    `available_tools` (the one documented case that's supposed to need an
    LLM). Fixed by explicitly passing an `OpenRouterModel` instance as
    `model=`.
11. **Positional pairing (`zip_longest`) between router invocations and tool
    outputs breaks when the two lists have different lengths for a legitimate
    reason** — e.g. a routing-only step given a synthetic tool name with no
    output of its own. From that point on, every later invocation silently
    inherited the wrong output. Fixed with the same name-based "match the
    earliest still-unfilled invocation" approach used in the task-completion
    script (see #16), verified against three distinct real orphaned-invocation
    cases (one added deliberately, one already present unmodified in a sample
    file) before trusting it.

### `task_complition_metric_test.py`

This script needed the most iteration of anything in the project — its docs
imply it needs full `@observe` tracing, with no standalone example given at
all (unlike every other DeepEval metric used here), and that gap between
documented and actual behavior produced most of the findings below.

13. **The standalone `LLMTestCase` + `.measure()` pattern does work**,
    confirmed empirically with real, coherent scores and reasoning — despite
    the metric's docs showing no example of this usage.
14. **DeepEval's own internal retries stacked against an added outer retry
    loop, multiplying total wait time** rather than improving reliability.
    DeepEval's own troubleshooting docs recommend the opposite of what seemed
    intuitive: *increase* the per-task timeout budget and *decrease* the
    retry count, rather than adding more retries on top.
15. **Context-window bug**: the first working version only gave the judge the
    current turn in isolation, so a request like "place one order" (with the
    product only named in an earlier turn) was scored as ambiguous even
    though the agent behaved correctly. Fixed by including prior conversation
    turns in the judge's context.
16. **That same fix introduced a new, different bug**: including the
    assistant's own *past replies* in the context caused a later turn to be
    scored as if it had re-performed an already-completed action from an
    earlier turn (a simple address-change turn was marked down for
    "placing an unrequested order" that had actually happened two turns
    earlier). Fixed by restricting context to prior *user* turns only,
    dropping assistant replies from what the judge sees.
17. **A standing, unresolved judge-reliability issue**: the same input,
    unchanged across three separate reruns, produced three different scores
    (0.75 → 0.3 → 0.8) for whether a short response contained a greeting —
    with the same factually wrong claim about the data each time. This wasn't
    fixed; it's flagged as a real limitation of this specific free judge
    model on certain fine-grained judgments, not something code can correct.
18. **`load_agent_history` assumed the input was always a bare list**, which
    broke on a dict-wrapped trace (`{"steps": [...]}`) — the same shape
    `data_extract_new.py` already knew how to handle, but this script never
    got the equivalent fix until it was tested against that file.
19. **Tool calls were invisible for the same trace shape** — the extraction
    logic only recognized `agent_action`/`tool_output` events, so a trace
    using single-event `tool_call`s (input and output together) silently
    registered zero tools used, even though real tool calls were present.
20. **The wrong "final answer" was being scored.** `find_agent_answer_in_window`
    returned the *first* matching answer-type step in a turn, which picked up
    an intermediate narration line ("Let me use my tool...") instead of the
    real final answer whenever a trace's schema reused the same event type for
    both. Confirmed with a real, concrete case: a score of 0.1 that was
    entirely an artifact of scoring the wrong sentence. Fixed to take the
    *last* matching step instead.
21. **A structural limitation, not a bug**: a pre-structured
    planner/router/tools trace has no recorded human turn and no distinct
    final answer, so task completion has nothing to score. Rather than a
    generic parsing error, the script now gives a specific explanation for
    this exact case.
22. A free model (`nemotron`) triggered a `"Structured outputs not
    supported"` warning and fell back to slower, less reliable plain-text
    generation — flagged as a plausible contributor to this script's timeout
    issues, never fully confirmed or chased down further.

## Known limitations (deliberately left as-is)

- **None of the five scripts consume `data_extract_new.py`'s `turns` field
  yet.** All still operate on the flattened, whole-trace view. Wiring the
  ground-truth-based scripts up to score one turn at a time is the natural
  next step, not yet done.
- **Precision/Recall/Planner match steps by position, not content.** A
  correctly-reordered plan would misreport as having missing or extra steps.
- **TC1's `"ai"` event type is used for both intermediate narration and the
  real final answer, with nothing in the schema to tell them apart.** The
  "take the last one" heuristic (Bug #20) is a reasonable assumption for every
  trace seen in this project so far, not a guarantee for every future one.
- **Task completion's judge-model reliability on some judgments is genuinely
  inconsistent** (Bug #17) — this is a property of the free model being used,
  not something any amount of code fixing resolves. Treat referenceless scores
  as directional, not precise, and cross-check the reasoning text before
  trusting a single run's number.
- **No monitoring for whether OpenRouter's `models` fallback array actually
  engages on a given run.** It was found unreliable (Bug #8) but there's no
  instrumentation to tell, on any given run, whether it fired or not.

## Design conventions used throughout

- **CLI args via `argparse`**, not hardcoded paths — every script takes
  `--predicted`/`--ground-truth`/`--output` (or `--history` for task
  completion).
- **Timestamped, project-root-anchored reports.** Every run writes its own
  `report/<name>_<timestamp>.json` rather than overwriting the last run,
  located via `find_dotenv()` so it works regardless of the working directory
  a script is invoked from.
- **Retry-with-backoff around every LLM judge call**, informed directly by
  real rate-limit and overload errors hit during testing — not a
  precautionary measure added speculatively.

## Running everything

From the project root:

```bash
make planner            # eval_tools/custom → Planner
make precision           # eval_tools/custom → Precision
make recall              # eval_tools/custom → Recall
make custom-all          # eval_tools/custom → all three

make tools               # eval_tools/deepeval → ToolCorrectnessMetric
make task_complition      # eval_tools/deepeval → TaskCompletionMetric
make deepeval-all         # eval_tools/deepeval → both

make all                 # every script, both subfolders, one command
```
